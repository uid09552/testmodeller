# UI

## Screens
1. **Projects**: the Project > Component > Feature > Model tree is the left
   navigation bar's main content, under the heading "Projects". There is no nav
   item for it — it is always there — and the cross-cutting views stay listed
   below it. Selecting a project, component or feature opens the Explorer page,
   which shows its detail.
2. **Model editor**: canvas (states, transitions), right panel with two tabs
   — Test Cases and Properties — scenario/test-case/validation/simulate tabs in
   the bottom panel, a floating AI chat window over the canvas, undo/redo,
   version history.
3. **Test cases**: generate dialog (criterion, seed), result list, coverage summary, diff on regenerate, export.
4. **Coverage dashboard**: per component/feature coverage and uncovered elements.
5. **Traceability**: backlog items traced to test cases, model elements and
   implementations, and the gaps (see below).
6. **AI assistant**: floating chat window in the model editor, and a proposal
   list page; prompt input, proposal cards with accept/reject and rationale.
7. **Threat Modeling**: a project's threat model, opened from the project tree —
   architecture, data-flow diagram, threats, risks, controls and security tests
   (see below).
8. **Settings**: shows the AI provider in effect, read-only, and how to change
   it in `.env`; the provider is configured in the environment, not here.

There is no model overview screen. A model is opened straight from the tree.

## Layout
```
+-----------+--------------------------------+-------------+
| Nav bar   |  Model canvas                  | Test cases  |
| + tree    |                                | | Props     |
|           |                                | | AI chat   |
+-----------+--------------------------------+-------------+
| Validation | Test cases | Coverage (bottom tabs)         |
+--------------------------------------------------------- +
```

## Navigation
- The tree is rendered once, in the nav bar, and is shared by every screen. It
  has no nav item of its own: collapsing the nav to icons is what hides it,
  because at that width there is no room for a tree.
- Single-clicking a model in the tree opens it in the model editor. Clicking a
  project, component or feature selects it and shows its detail on the Explorer
  page.
- Navigating to a model passes the feature id along, because the AI endpoints
  are scoped to a feature.

## What the editor saves (ADR 0010)
- Everything the user changes in the editor is saved with the model by
  autosave: the graph (states, transitions, positions, guards, actions), and
  in the model's `layout` the presentation — each state's shape, size,
  decision kind and style, groups, each transition's curves, connector dots
  and style, the notes and text boxes, and test display numbers. A reload or
  another browser shows the model as it was left.
- A model without layout (made through the API, by import of an old export,
  or by AI) shows the defaults; so does any element the layout does not
  mention. Layout entries for deleted elements are dropped on the next save.
- Restoring a version restores its layout; a duplicate keeps the layout.
- The model's variables are kept on every save, although the editor cannot
  edit them yet. Only the three-way status (`review`) and view state (zoom,
  pan, selection) are not stored with the model.

## Canvas tools
- The toolbar carries a select/pan pair next to Align, as a segmented control:
  they are modes, so the active one stays lit. `V` selects, `H` pans.
- **Select** is the editing default: dragging the background marquee-selects,
  dragging a state moves it, and the connector dots are offered on hover.
- **Pan** is the hand tool: a left-drag moves the view wherever it starts, over
  a state as readily as over the background, and no connector dots are offered.
  The cursor is `grab`, and `grabbing` while dragging.
- Middle-mouse and Shift/Alt + left-drag pan in either mode, so panning never
  requires switching tool.
- Double-clicking empty canvas centres the diagram. It does not add a state: an
  easy gesture should not be destructive on a diagram being read. States are
  added from the palette, by dragging off a connector dot, or from the
  right-click menu.

## Views: Canvas, Table, Present
The editor header switches between three views; the choice is in the URL
(`?view=table`, `?view=present`), so a link opens the same view.

- **Present** shows the model read-only for reviews: the editing toolbar,
  palette, side column and bottom panel are hidden; dragging pans; nothing can
  be added, moved, reconnected, renamed or deleted. Zoom, search, the minimap
  and highlights still work. Esc or "Edit" returns. It is a choice, not a
  permission: the server still decides who may change a model.
- **Table** (the keyboard alternative of NFR-004) lists the states (name,
  kind, test cases, outgoing transitions, issues) and the transitions (from,
  event, guard, action, expected result, to, issues) as grids. Every field is
  editable: arrows move between cells, Enter or F2 edits, Enter saves, Esc
  cancels, Delete pressed twice deletes the row (a state with its
  transitions), "Add state" / "Add transition" add rows. Edits share the
  canvas's undo history (Ctrl+Z / Ctrl+Y) and are saved the same way.
- Each transition's **expected result** (used by generated tests) is editable
  in the table and in the Properties panel, and is kept on save.

## Test path highlight
- "Show path" on a test case (Test Cases tab, Test Cases page, Traceability
  matrix) highlights the states and transitions it is assigned to and dims
  the rest. Highlighted elements are drawn thicker and carry their step
  numbers ("2, 5" for a transition taken twice); dimmed ones are faded and
  dashed, so the difference is not colour alone. A banner names the test and
  its number of steps, and each highlighted element's accessible name ends
  with its steps. The first step is brought into view.
- From another page the model opens with `?highlight=<testCaseId>`.
- Esc or "Clear" ends the highlight. A test the database has not saved yet
  highlights only its state.

## Simulation
- The **Simulate** tab of the bottom panel steps through the model. Start puts
  it in the initial state with the variables' initial values; the tab lists
  the variables and every outgoing transition: enabled ones as buttons,
  blocked ones with the guard that is false (or the evaluation error).
  Taking one moves on; Step back, Restart and Stop are offered.
- The canvas marks the current state ("▶ now") and draws enabled transitions
  bold and blocked ones dashed.
- A state with no enabled transition that is not final is reported as stuck.
- It simulates the model as it is on screen, unsaved edits included, using
  `POST /models/{id}/simulate`, so guards and actions behave exactly as in
  test generation. A model with validation errors cannot be simulated; the
  errors are listed.
- **Save as test case** stores the trail as a manual test case of the feature,
  named "Simulation: A → B → …", with one step per transition (event as
  action, "State 'X' is reached" as expected result), assigned to its
  transitions and states in step order.

## Canvas navigation
- **Zoom:** the toolbar zooms in and out, centres the diagram, resets the view,
  **zooms to fit** the whole model (Shift+1) and **zooms to the selection**
  (Shift+2). Fitting stays within 30%–300% and never zooms in past 200%.
- **Search:** Ctrl+F (while the canvas has focus) or the toolbar's search
  button finds states by name and transitions by event or guard, states first,
  in reading order. The first hit is selected and brought into view; Enter
  and Shift+Enter step through the hits ("2 of 5"), "No matches" leaves the
  selection alone, and Esc closes the search.
- **Minimap:** an overview in the bottom-right corner shows every state and
  the visible area; clicking or dragging in it moves the view there. It can be
  hidden from the toolbar; that choice is remembered in this browser.
- **Collapsed groups:** "Collapse Group" (context menu) folds a group into one
  box with its name and number of states. Transitions to and from its states
  end on the box; transitions inside it are hidden. Double-click, the box's +,
  Enter or "Expand Group" restores the states where they were. Showing a
  hidden state (search, validation, a test) expands its group. The collapsed
  state is saved with the layout.
- **Snapping:** while a state is dragged it snaps to an 8 px grid and lines up
  with the edges and centres of nearby states, shown by dashed guide lines.
  The toolbar switches snapping off (remembered in this browser); holding Alt
  suspends it.

### Keyboard shortcuts
All are listed in the canvas with `?`, from the same table the canvas uses.
Those marked * act only while the canvas has keyboard focus, so they do not
take keys from the rest of the page.

| Keys | Action |
| --- | --- |
| Tab / Shift+Tab * | Next / previous state, in reading order (top to bottom, left to right), with a focus ring |
| Ctrl+Tab * | Next transition |
| Arrows, Shift+Arrows * | Move the selection 8 px / 80 px; a burst of presses is one undo step |
| F2 * | Rename the selected state, or edit the selected note |
| + / − * | Zoom in / out |
| Ctrl+F * | Search |
| Shift+1 / Shift+2 | Zoom to fit / to the selection |
| Ctrl+Z, Ctrl+Y | Undo, redo |
| Ctrl+A, Ctrl+G | Select all states, group the selection |
| V / H | Select / pan tool |
| Delete, Backspace | Delete the selection |
| Esc | Cancel, close menus, search and help |
| ? | Show the shortcuts |

Together with the Properties panel, this makes positioning, selecting and
editing states and transitions possible without a mouse. The table view that
NFR-004 also asks for is part of `model-review-modes`.

## Transition routing
- Selecting a transition shows its handles: both ends (drag onto another
  connector dot to re-attach), a diamond **bend handle** in the middle, and
  round **bend points** (waypoints) if it has any.
- Dragging the bend handle bends the transition through the pointer;
  double-clicking it straightens the transition.
- **Bend points:** Alt+click on a transition, or "Add Bend Point" in its
  context menu, adds one on the nearest segment. Drag to move, double-click
  to remove. A curved transition runs smoothly through its bend points.
  Moving a state leaves the bend points where they are; moving a group moves
  the bend points of transitions wholly inside it.
- **Routing style:** curved (default) or right-angle, from the context menu or
  the Properties panel. Right-angle transitions leave and enter states at a
  right angle to the side of their connector dots. They do not route around
  states: add bend points to steer them.
- **Labels:** drag a transition's label (its guard moves with it) away from
  the line; a dotted leader line then joins it to the transition. "Reset
  Label Position" (context menu or Properties panel) returns it.
- **Self-loops** are drawn on the side of their connector dot; several on the
  same side are drawn at increasing sizes so none overlaps.
- The Properties panel offers all of it without a mouse: routing style,
  Straighten, a bend point list with remove buttons, Reset label position.
- Routing is presentation: it is undoable, saved in the model's layout, and
  changes nothing about the model's behaviour.

## Shapes and styles
- **Shapes:** a state is drawn as a circle, rectangle, diamond, hexagon,
  parallelogram, cylinder or document, chosen in the Properties panel or the
  context menu ("Make Hexagon", …). A shape never changes the state's kind,
  and every shape has the same four connector dots, on its outline. The kind
  still decides the default look (initial is filled, final has a double
  outline, decision is amber).
- **Style section** of the Properties panel, for states and transitions:
  - **Line:** pattern (solid, dashed, dotted), width (1–4 px) and colour.
    Dashes scale with the width.
  - **Fill** colour (states only). On a dark fill the name turns light,
    unless a text colour is set.
  - **Arrowhead** (transitions only): filled (default), open or line ("V"),
    in the line's colour. A transition always keeps an arrowhead.
  - **Text:** colour, size (small, normal, large), bold and italic. A
    transition's guard follows its label's colour and size. A state grows to
    fit a larger or bolder name.
  - Every colour control offers "Default", the preset palette, and "Custom"
    (the browser's colour picker). A custom colour shows as the current value.
- **Several elements:** with several states and transitions selected, the
  panel shows the style controls they all support (a state and a transition
  share line and text, not fill or arrowhead). A change applies to each of
  them as one undo step; a control whose values differ shows "Mixed".
- **Status cues come first:** while the coverage overlay, a test path
  highlight, the simulation or the selection marks an element, its cue is
  drawn over the user's style (colour, width and dash), and the user's style
  returns when the cue ends. Cues also carry a non-colour sign (a "0"
  marker on uncovered states and transitions, step numbers, "▶ now", the
  selection ring), so a user style cannot imitate them.
- Styles show in present mode and are presentation only: undoable, saved in
  the layout, and without effect on validation, generation or coverage.

## Notes and text boxes
- The palette offers a **note** (a pale yellow box with a folded corner) and a
  **text** box (text without border or fill). Dropping one on the canvas
  opens its text editor.
- Double-click or F2 edits the text in place: Shift+Enter adds a line, Enter
  commits, Escape restores the previous text. The Properties panel has the
  same text field. Text wraps to the box's width and a note grows taller to
  fit it. Text is limited to 2,000 characters; longer pasted text is cut, and
  the editor says so. An annotation left empty is removed.
- Annotations are selected, moved, resized (eight handles), aligned, snapped,
  marquee-selected and deleted like states, and moving them together with
  states is one undo step. Notes take line, fill and text style; text boxes
  take text style.
- They are **not part of the model**: they live only in the layout. Validation,
  generation, coverage, staleness, simulation, search, the table view, the AI
  and exported test cases never see them, and a transition cannot start or end
  on one (dropping a transition's end on a note creates nothing). A duplicated
  model keeps its notes.
- Present mode shows them read-only.

## Coverage overlay (FR-022)
- A **Coverage** toggle in the canvas toolbar highlights the states and
  transitions no test case covers, without changing the model. It is
  editor-local and not saved.
- A dropdown chooses what counts: states and transitions, states only, or
  transitions only (the only criteria `GET /models/{id}/coverage` supports).
  The toolbar shows the counts, e.g. "3/5 states, 4/7 transitions".
- **States** are computed live from the tests in the editor, the same rule as
  the test chips: a state with at least one test case is covered. Adding a test
  updates the highlight at once, without a save.
- **Transitions** come from `GET /models/{id}/coverage` for the saved model,
  fetched when the overlay shows transitions and again after each save. While
  the model has unsaved changes the figure says "(as of last save)"; before
  the first successful fetch it says "transitions unavailable until saved"
  rather than showing zero.
- An uncovered element gets a dashed amber outline; a state also gets a "0"
  marker, and both carry an accessible label ending "not covered by any test
  case", so the cue does not rely on colour.
- Clicking a highlighted state selects it and opens the right column on its
  Test Cases, where **Add** creates a test case for it.

## Stale generated tests
- The editor asks `GET /models/{id}/stale-tests` when a model opens and after
  every save (the UI has no generate action of its own; generated test cases
  arrive through the API and are checked on the next open or save). The answer
  is never acted on automatically: the user regenerates, edits or deletes.
- **Test Cases tab:** the header shows "⚠ N stale" when the model has stale
  tests (clicking it opens Validation); each stale test carries a "⚠ Stale"
  badge and its reasons as text.
- **Canvas chips:** a state with stale tests gets an extra "!" chip, and the
  chips' accessible label adds ", N stale".
- **Validation tab:** each stale test is a warning (`STALE_TEST`) on its
  state, with the reasons.
- **Test Cases page:** stale rows carry the "⚠ Stale" badge and the reasons
  under the name.
- Markers combine a symbol and text, never colour alone. Manual, AI and
  per-state editor tests have no path and are never marked.

## Test results (FR-050 to FR-053)
- **Import:** the Test Cases page has an **Import results** button. The dialog
  asks for the project (preselected from the project filter), the file and the
  format (JUnit XML or Cucumber JSON, guessed from `.xml` / `.json`). Files over
  10 MB are refused before upload. **Preview** runs the import as a dry run and
  shows what would be recorded; **Import** records. The report gives the
  number of results, matched, recorded and already imported, and lists the
  unmatched and ambiguous names. A rejected file shows the server's reason.
- **Matching:** a result is matched by the tag `@tm-<test case id>`, otherwise
  by exact test case name within the project; a name shared by several test
  cases is ambiguous and not recorded. Importing the same file twice records
  nothing new.
- **Carrying the tag:**
  - *Cucumber:* the Gherkin export (backend and Test Cases page) puts
    `@tm-<id>` on every scenario; Cucumber reports scenario tags in its JSON,
    so nothing else is needed.
  - *JUnit:* put the tag in the test name (e.g. `it('logs in @tm-<id>')` in
    Jest/Playwright, `@DisplayName("logs in @tm-<id>")` in JUnit 5) or the
    classname, or add a test case property `tmId` with the id (e.g.
    Playwright annotations or the `record_property("tmId", ...)` fixture in
    pytest). The CSV export has a `tmId` column with the tag of each test case.
- **Display:** the latest result is a badge with a symbol and a word — "✓
  Passed", "✗ Failed", "⚠ Error", "– Skipped" — on the Test Cases page rows,
  the editor's Test Cases tab and the Traceability matrix (also in its CSV).
  The tooltip has the message. A state's chips get a "✗N" chip for tests
  whose latest result failed or errored, and the chips' label adds ", N
  failing".
- **Coverage:** once a model has results, the coverage overlay adds the
  passing count, e.g. "3/5 states (2 passing), 4/7 transitions (3 passing)". An
  element is passing when every test covering it last passed. The Coverage
  dashboard page still shows placeholder data and is not part of this.

## Test case visibility (FR-033)
- Each state on the canvas carries a chip per test category (`U`/`I`/`F`) with
  its count, and a dot when the category contains a negative case. The chips
  are the primary signal that a state is covered, so they are rendered at
  readable size with filled, high-contrast backgrounds.
- The chips sit just below the state, not inside it: at a readable size they
  covered the state's own name.
- A state sizes itself to its name: long names wrap onto further lines (up to a
  per-shape maximum line width, measured in the name's font size and weight)
  and the state grows, around its centre, until the text fits inside the
  outline. It updates live while typing, applies on
  load, and never goes below the shape's default size. Size is local editor
  layout and is not part of the API.
- A state's name may contain line breaks. In the inline editor Shift+Enter
  inserts one, Enter commits and Escape restores the old name; the Properties
  panel label field is multi-line too. Each explicit line is wrapped on its
  own and the state is sized for all lines, live while typing. Trailing blank
  lines are dropped on commit. Outside the canvas (validation messages, test
  exports and lists) a name is shown on one line, breaks becoming spaces. The
  API's state `name` already allows this, so the contract is unchanged.

## Validation (editor)
- The error/warning count in the canvas toolbar is a button: it opens the
  Validation tab of the bottom panel, un-collapsing the panel if it was hidden.
  A valid model shows a plain indicator that does nothing.
- Clicking an issue row (or pressing Enter/Space on it) selects the state or
  transition it concerns and pans it into view when it is off-screen; zoom is
  left alone. A row without an element is not clickable.
- Double-clicking a state's test chips selects the state, opens the right panel
  on the Test Cases tab and scrolls the list into view, highlighting it
  briefly. The gaps between chips are part of the control.
- Test Cases is a tab of its own and the right panel's default, because test
  cases are what the tool is for. With a state selected it edits that state's
  cases; with nothing selected it lists the states that have any, so the tab is
  never empty for no reason. The tab shows the model's total.
- The test case overlay closes only through Save, Cancel or the close button in
  its top-right corner. Clicking the backdrop, releasing a text-selection drag
  outside the dialog, and pressing Escape do not close it, so unsaved edits are
  never lost by accident.

## Test Cases page (FR-004, FR-005, FR-024)
- Lists every test case across all projects, one row per case, with its
  Component > Scenario > Model › State path. Double-clicking a row edits its
  Gherkin.
- **Filters**: project, component, scenario and model dropdowns cascade:
  each only offers values inside the levels above it, and changing a level
  clears the levels below. Category chips are multi-select (none = all); type
  (positive/negative) is single-select; a links filter narrows to cases with or
  without an implementation link, with a backlog item, or with no links. Search
  matches the id, name, path, state and the Given/When/Then text. A "Clear
  filters" button appears with the number of active filters.
- **Sorting**: every data column header sorts; clicking the active header flips
  the direction, and `aria-sort` reflects it. The id sorts by model, then
  numerically by sequence, so `M_2` precedes `M_10`. Ties fall back to the id.
- **Grouping**: by project, component, scenario, model, state, category or
  type. Each group has a collapsible header row with its path, count and
  positive/negative split; the column sort applies within groups. Expand all /
  Collapse all are offered while grouped.
- The summary tiles and the Gherkin export cover exactly the filtered rows.
- Filters, sort and grouping are remembered in browser storage; they are a
  per-browser convenience, not stored server-side.

## Traceability page (FR-025 to FR-028)
- **Requirement means backlog item.** A requirement is identified by the backlog
  link of a test case (its `backlogUrl`); there is no separate requirement
  entity. Links that differ only by trailing slash, fragment or the case of the
  scheme and host are one item. The implementation link (`implementationUrl`) is
  the code or work that realises a test case. Both are fields of the test case,
  set in the test case editor, and must be full http(s) URLs.
- The page is `GET /projects/{projectId}/traceability` for one project, chosen
  in a dropdown (it opens on the first). Component and scenario dropdowns
  cascade as on the Test Cases page.
- **Matrix tab**: one row per test case, grouped under its backlog item (rows
  with no backlog link are grouped as "No backlog item"). Columns: backlog item,
  test case, Component › Scenario, number of assigned model elements, and
  implementation link. A gap dropdown (any trace, no backlog item, no
  implementation, no model element) is applied by the server; the search box
  matches test case name, backlog URL and implementation URL in the shown rows.
- **Gaps tab**: three tiles with the counts of the gap types, each selecting
  that gap and listing it: test cases without a backlog item, test cases of a
  backlog item without an implementation link, and backlog items whose test
  cases are assigned to no state or transition. The counts do not change with
  the gap or search.
- A test case name opens the test case editor (through the Test Cases page,
  `?open=<testCaseId>`). Links open in a new tab with `rel="noopener noreferrer"`;
  a value that is not http(s) is shown as text, never as a link.
- **Export CSV** writes the shown rows, one line per backlog item and test case
  pair (an untraced test case has an empty backlog cell). Cells that start with
  `=`, `+`, `-` or `@` are prefixed with `'`, so a spreadsheet does not run them.
- Test results are not part of this page.

## AI chat panel (FR-030 to FR-034)
- The chat is a window floating over the bottom-right corner of the canvas,
  opened and closed with an "AI" button there; the button shows the number of
  proposals waiting for a decision. The window can be minimised to its title
  bar and resized, and keeps its transcript while it is closed. It is not
  shown in Present mode. Opening another model clears it: its proposals
  belong to the feature that was open.
- Before the first request of a turn the panel syncs the open model's project,
  component, feature and graph to the backend and reuses the resulting ids
  afterwards, because the AI endpoints are scoped to a feature the backend
  knows (ADR 0006).
- A message is turned into a `POST /ai/proposals` request. The requested kind is
  either chosen explicitly in the composer or inferred from the message:
  test cases -> `test-cases`, scenario description -> `feature-description`,
  states/transitions -> `states-and-transitions`, whole model -> `model`.
- The panel polls `GET /jobs/{id}` until the job finishes, then loads each
  proposal and renders it as a card with its rationale, its source model and
  Accept / Reject.
- Accept calls `POST /proposals/{id}/accept` and only then applies the payload
  to the open model: a test case is attached to the selected state, a scenario
  description replaces the model's scenario text, states and transitions are
  added to the canvas. Nothing is applied before the user accepts (FR-033).
- Errors are shown in the transcript using the problem detail returned by the
  API. The one prerequisite the panel cannot satisfy itself is an AI provider
  configured in Settings; a model that is not in the tree at all is reported as
  such, because there is no feature to ask about.

## Behaviors
- Proposals appear as ghost elements on the canvas until accepted.
- Unsaved changes are indicated; conflicts (version mismatch) prompt reload/merge.
- Keyboard-accessible alternative to canvas editing (table view of states/transitions).

## Threat Modeling (FR-060 to FR-076)
See [09-threat-modeling.md](09-threat-modeling.md) for the rules behind it.

- **Navigation:** there is no nav item. A project's threat model is listed in
  the project tree directly under the project, with a shield icon of its own
  and the threat model's name; clicking it opens
  `/threat-modeling/<projectId>/<tab>`. A project without a threat model has no
  such item. Right-clicking a project offers **New Threat Model** (named after
  the project, then opened) or, when it has one, **Open Threat Model**; the
  item's own menu offers **Open Threat Model** and **Delete Threat Model**
  (confirmed, since everything in it goes too). Without a project in the URL the
  workspace opens the first project; a project dropdown switches project and
  keeps the tab.
- **No threat model yet:** the page says so and offers "Create threat model"
  (with an optional name). Nothing is created by opening the page.
- **Tabs:** Overview, Diagram, Components, Data Flows, Zones, Assets, Threats,
  Risks, Controls, Security Tests, as a tab list: arrows move focus, Enter or
  a click opens a tab, and the tab is in the URL. A `?select=<id>` opens that
  item's editor; `?target=<id>` filters the Threats tab to a component or flow.
- **Tables:** every list is a table with a text filter, sortable headers
  (`aria-sort`), rows reachable with Tab and the arrows, and Enter (or a
  click on the first cell) opening the item's editor in a side panel. Escape
  or Cancel closes the panel; errors from the server are shown in it. Every
  write reloads the threat model, so computed values (crossings, warnings,
  levels, flags, staleness) are always the server's. A save over someone
  else's newer version says so and asks for a reload.
- **Components:** type (grouped by layer), zone, internet exposure,
  criticality, owner, technology, assets, an optional mapping to a Feature (and
  its Component) of the project tree, and the missing-information warnings.
  Features are created in the project tree, not here: the editor lists them
  grouped by their component, a "Feature" column shows the mapping as
  "Component › Feature" (a dash when none), and picking a feature also maps its
  component if none is mapped. Deleting one
  says how many data flows go with it.
- **Data Flows:** from/to, relationship, label, protocol, both ways,
  authentication ("Not documented", "None" or a method), encryption, assets.
  The "Trust boundary" column reads "⇢ Crosses (0 → 3)"; a toggle shows only
  crossing flows.
- **Zones:** kind and trust level 0 (untrusted) to 4; deleting a zone says its
  components will have no zone.
- **Assets:** category, C/I/A, personal data, owner, and the components and
  flows that handle it — editable from the asset as well as from the
  component or flow.
- **Threats:** filters by status, category, origin, current risk and target.
  Candidates read "◌ Candidate". "Suggest threats" applies the STRIDE rules
  and says how many candidates were added, or that there were none. Rows have
  checkboxes for **Confirm** (to open) and **Dismiss** (asks for a reason). A
  rule threat's editor shows why it was suggested — the rule, the facts, what
  would confirm or dismiss it — and its recommended controls, each with "Add
  as control" (a planned control linked to the threat). Flags read "No
  control", "Controls planned only", "✗ Failing test", "Overdue".
- **Risks:** the 5 × 5 matrix of open and accepted threats, current or
  inherent; each cell is a button naming its likelihood, impact, level and
  count, and selecting one filters the register. The register lists
  inherent and current score and level (a symbol and a word), treatment,
  owner and due date ("⚠ Overdue"), and exports as CSV. Its editor sets the
  ratings ("not assessed" until set), treatment — accept asks for a rationale
  and who accepts — owner and due date. "Change levels" edits the
  thresholds; a gap or overlap is refused with the server's reason.
- **Controls:** type, category, status (the verification date is shown),
  owner, acceptance criteria, threats and components; filters by status and
  by "without threats" / "without tests"; the editor lists the control's
  security tests.
- **Security Tests:** a list of its own, not on the Test Cases page. Filters by
  status, type and latest result. "Generate tests from threats" generates
  drafts for chosen threats (or all open and accepted ones) and reports what
  was created and skipped. **Mark ready** works on the checked rows. A ready
  test's editor offers **Record result** (passed, failed or not run, with a
  note). Badges read "✓ Passed", "✗ Failed", "– Not run" and "⚠ Stale: …".
  CSV and Gherkin export cover exactly the tests the table shows.
- **Overview:** counts (components, assets, flows, crossings, open threats,
  controls verified, missing information, overdue), threats by status and by
  level, the current-risk matrix, and the open threats without a control and
  controls without a test, each a link to its item. An empty model prompts
  for its first component. The scope fields (scope, objectives, assumptions,
  exclusions) are edited and saved here.
- **Diagram:** it draws and styles like the model editor's canvas, and uses
  the full width and the height of the window left below the toolbar.
  Components are shapes by layer (external entities rectangles, data stores
  cylinders, the rest rounded boxes) with name and type; zones are dashed
  regions labelled with their trust level. Flows are arrows between
  **connector dots** (top, right, bottom, left of each component): a flow drawn
  on the diagram keeps the dots it was drawn between, and a flow made in a
  table joins the facing sides, never the centres. Labels sit on a small
  background as in the editor; a two-way flow has arrowheads at both ends. A
  flow that crosses a trust boundary has a diamond where it leaves the zone,
  and its accessible name ends "crosses trust boundary".
  - *Editing:* choose a type and **Add component**; drag from a connector dot
    to another component to add a flow (its editor opens); double-click or
    Enter opens an editor (a zone's opens on the Zones tab); dragging a
    component into or out of a region changes its zone; dragging a zone's
    header moves it with its components, its corner resizes it; Delete
    removes the selection after confirming. Edits are the same saves the
    tables make.
  - *Flows:* a selected flow shows its two ends — drag one to another dot to
    re-attach it, or onto another component to change the flow's source or
    target — and, when curved, a diamond bend handle (double-click
    straightens). Routing is curved or right-angle.
  - *Detail view:* clicking a component, flow or zone (not dragging it)
    opens its detail view with two tabs. **Details** is the element's form
    (name and the other fields, as in the tables); **Properties** is the
    style controls below. Selecting another element replaces it and clearing
    the selection (Escape, a click on the background) closes it. With
    several elements selected (Shift+click), "Properties…" in the right-click
    menu opens a Properties panel beside the diagram for all of them. The
    style controls are the model editor's: the model editor's style section — line colour, pattern and
    width, fill (components and zones), text colour, size, bold and italic,
    the arrowhead of flows — plus a component's shape, a flow's routing and
    Straighten, "Edit details…" and "Reset style". With several elements
    selected a change applies to all of them, and differing values show as
    mixed. The selection is a dashed ring, so no style can hide it.
  - *Right-click menus* (also the context-menu key or Shift+F10 on a focused
    component; arrows move, Escape closes): on a component — Edit Details,
    Properties… (the Properties tab of the detail view), Add Data Flow, Shape by Type / Make <shape>, Move to <zone> / Remove from
    Zone, Show Threats, Delete Component; on a flow — Edit Details, Properties…, Reverse
    Direction, Curved / Right-Angle Routing, Straighten, Show Threats, Delete
    Data Flow; on a zone — Edit Details, Properties…, Fit to Contents, Delete Zone; on the
    background — Add <type> Here (in the zone at that point), Add Zone Here,
    Zoom to Fit, Show Threat Badges.
  - *Threats* toggle: a badge with the number of open threats and the highest
    level, linking to the Threats tab filtered to that element.
  - *Navigation:* zoom buttons, + / −, wheel, Fit and Shift+1, drag the
    background to pan, snapping while dragging (Alt suspends it), a minimap,
    Tab / Shift+Tab between components in reading order, arrows move the
    focused one.
  - *Layout:* positions, region bounds, shapes, styles, and each flow's dots,
    routing and bend are saved with the threat model, opaque to the server and with their own
    version, a moment after a change. Components the layout does not know are
    placed where they overlap nothing; entries of deleted items are dropped on
    the next save. The layout changes nothing about crossings, threats, risks
    or tests.

## Threat Modeling assurance (FR-077 to FR-084)
- **Risks:** the register shows inherent, current and residual score and level; the matrix has a selector for the three views. Residual is entered beside the other ratings. Flags `Residual above current`, `Unsupported residual` and `Acceptance expired` read as warnings.
- **Acceptance:** choosing treatment *accept* asks for rationale, approver and expiry date. An expired acceptance shows the threat as open with its earlier record visible.
- **Controls:** each control has an evidence list (add, delete). *Verified* is offered only when evidence exists; a review-by date can be set; overdue controls are flagged.
- **Editors:** threat, asset and flow editors have the new detail fields; an entry-point flow is marked in the table and on the diagram; a threat shows its affected trust boundaries.
- **Baselines:** a tab listing baselines with *Create baseline* (name, note), *Open*, *Compare* and *Delete*. *Open* shows the baseline as a read-only report (scope, architecture, assets, matrices, register, controls with evidence, flags) with a banner of name and date and no editing; the diagram is not part of it.
- **Report:** *Report* opens the assessment report of the live model or of a baseline, with *Print* and *Export Markdown*; the print stylesheet hides the application chrome.
- **Overview:** completeness findings (linked to the entity), acceptances expiring within 30 days and overdue verifications.

## Threat Modeling assistant (FR-085 to FR-089)
- **Window:** as in the model editor, an *AI* launcher in the bottom-right corner of the workspace opens a chat window floating over the page, on every tab. It can be resized by its top-left grip, minimised and closed; closing keeps the conversation, and the proposals waiting for a decision are counted on the launcher. The transcript lives in the browser; each message is one request and nothing earlier is sent. A kind selector overrides the kind inferred from the text; a selected entity is offered as the focus ("about THR-4").
- **Cards:** one card per proposal with the content, the rationale and the source model, and *Accept*, *Edit*, *Reject*. Accepting calls the server first and updates the workspace after it succeeds. Architecture cards list new and already existing elements; rating cards show the old and the proposed rating; review answers are text with links and no accept button.
- **Disabled:** with provider `none` or AI off for the threat model the panel explains why and, for editors, offers *Enable AI assistance* with the provider and endpoint host named. *Preview context* shows what would be sent.
- **Badge:** entities with origin `ai` carry an *AI* badge in tables and in the editors.
