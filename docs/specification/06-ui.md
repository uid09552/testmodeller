# UI

## Screens
1. **Projects**: the Project > Component > Feature > Model tree is the left
   navigation bar's main content, under the heading "Projects". There is no nav
   item for it — it is always there — and the cross-cutting views stay listed
   below it. Selecting a project, component or feature opens the Explorer page,
   which shows its detail.
2. **Model editor**: canvas (states, transitions), right panel with three tabs
   — Test Cases, Properties and AI — validation/test-case/scenario tabs in the
   bottom panel, undo/redo, version history.
3. **Test cases**: generate dialog (criterion, seed), result list, coverage summary, diff on regenerate, export.
4. **Coverage dashboard**: per component/feature coverage and uncovered elements.
5. **Traceability**: backlog items traced to test cases, model elements and
   implementations, and the gaps (see below).
6. **AI assistant**: chat panel in the editor's right column, and a proposal
   list page; prompt input, proposal cards with accept/reject and rationale.
7. **Settings**: shows the AI provider in effect, read-only, and how to change
   it in `.env`; the provider is configured in the environment, not here.

There is no model overview screen. A model is opened straight from the tree.

## Layout
```
+-----------+--------------------------------+-------------+
| Nav bar   |  Model canvas                  | Test cases  |
| + tree    |                                | | Props     |
|           |                                | | AI chat   |
+-----------+--------------------------------+-------------+
| Validation | Test cases | Coverage (bottom tabs)         |
+--------------------------------------------------------- +
```

## Navigation
- The tree is rendered once, in the nav bar, and is shared by every screen. It
  has no nav item of its own: collapsing the nav to icons is what hides it,
  because at that width there is no room for a tree.
- Single-clicking a model in the tree opens it in the model editor. Clicking a
  project, component or feature selects it and shows its detail on the Explorer
  page.
- Navigating to a model passes the feature id along, because the AI endpoints
  are scoped to a feature.

## Canvas tools
- The toolbar carries a select/pan pair next to Align, as a segmented control:
  they are modes, so the active one stays lit. `V` selects, `H` pans.
- **Select** is the editing default: dragging the background marquee-selects,
  dragging a state moves it, and the connector dots are offered on hover.
- **Pan** is the hand tool: a left-drag moves the view wherever it starts, over
  a state as readily as over the background, and no connector dots are offered.
  The cursor is `grab`, and `grabbing` while dragging.
- Middle-mouse and Shift/Alt + left-drag pan in either mode, so panning never
  requires switching tool.
- Double-clicking empty canvas centres the diagram. It does not add a state: an
  easy gesture should not be destructive on a diagram being read. States are
  added from the palette, by dragging off a connector dot, or from the
  right-click menu.

## Coverage overlay (FR-022)
- A **Coverage** toggle in the canvas toolbar highlights the states and
  transitions no test case covers, without changing the model. It is
  editor-local and not saved.
- A dropdown chooses what counts: states and transitions, states only, or
  transitions only (the only criteria `GET /models/{id}/coverage` supports).
  The toolbar shows the counts, e.g. "3/5 states, 4/7 transitions".
- **States** are computed live from the tests in the editor, the same rule as
  the test chips: a state with at least one test case is covered. Adding a test
  updates the highlight at once, without a save.
- **Transitions** come from `GET /models/{id}/coverage` for the saved model,
  fetched when the overlay shows transitions and again after each save. While
  the model has unsaved changes the figure says "(as of last save)"; before
  the first successful fetch it says "transitions unavailable until saved"
  rather than showing zero.
- An uncovered element gets a dashed amber outline; a state also gets a "0"
  marker, and both carry an accessible label ending "not covered by any test
  case", so the cue does not rely on colour.
- Clicking a highlighted state selects it and opens the right column on its
  Test Cases, where **Add** creates a test case for it.

## Stale generated tests
- The editor asks `GET /models/{id}/stale-tests` when a model opens and after
  every save (the UI has no generate action of its own; generated test cases
  arrive through the API and are checked on the next open or save). The answer
  is never acted on automatically: the user regenerates, edits or deletes.
- **Test Cases tab:** the header shows "⚠ N stale" when the model has stale
  tests (clicking it opens Validation); each stale test carries a "⚠ Stale"
  badge and its reasons as text.
- **Canvas chips:** a state with stale tests gets an extra "!" chip, and the
  chips' accessible label adds ", N stale".
- **Validation tab:** each stale test is a warning (`STALE_TEST`) on its
  state, with the reasons.
- **Test Cases page:** stale rows carry the "⚠ Stale" badge and the reasons
  under the name.
- Markers combine a symbol and text, never colour alone. Manual, AI and
  per-state editor tests have no path and are never marked.

## Test results (FR-050 to FR-053)
- **Import:** the Test Cases page has an **Import results** button. The dialog
  asks for the project (preselected from the project filter), the file and the
  format (JUnit XML or Cucumber JSON, guessed from `.xml` / `.json`). Files over
  10 MB are refused before upload. **Preview** runs the import as a dry run and
  shows what would be recorded; **Import** records. The report gives the
  number of results, matched, recorded and already imported, and lists the
  unmatched and ambiguous names. A rejected file shows the server's reason.
- **Matching:** a result is matched by the tag `@tm-<test case id>`, otherwise
  by exact test case name within the project; a name shared by several test
  cases is ambiguous and not recorded. Importing the same file twice records
  nothing new.
- **Carrying the tag:**
  - *Cucumber:* the Gherkin export (backend and Test Cases page) puts
    `@tm-<id>` on every scenario; Cucumber reports scenario tags in its JSON,
    so nothing else is needed.
  - *JUnit:* put the tag in the test name (e.g. `it('logs in @tm-<id>')` in
    Jest/Playwright, `@DisplayName("logs in @tm-<id>")` in JUnit 5) or the
    classname, or add a test case property `tmId` with the id (e.g.
    Playwright annotations or the `record_property("tmId", ...)` fixture in
    pytest). The CSV export has a `tmId` column with the tag of each test case.
- **Display:** the latest result is a badge with a symbol and a word — "✓
  Passed", "✗ Failed", "⚠ Error", "– Skipped" — on the Test Cases page rows,
  the editor's Test Cases tab and the Traceability matrix (also in its CSV).
  The tooltip has the message. A state's chips get a "✗N" chip for tests
  whose latest result failed or errored, and the chips' label adds ", N
  failing".
- **Coverage:** once a model has results, the coverage overlay adds the
  passing count, e.g. "3/5 states (2 passing), 4/7 transitions (3 passing)". An
  element is passing when every test covering it last passed. The Coverage
  dashboard page still shows placeholder data and is not part of this.

## Test case visibility (FR-033)
- Each state on the canvas carries a chip per test category (`U`/`I`/`F`) with
  its count, and a dot when the category contains a negative case. The chips
  are the primary signal that a state is covered, so they are rendered at
  readable size with filled, high-contrast backgrounds.
- The chips sit just below the state, not inside it: at a readable size they
  covered the state's own name.
- A state sizes itself to its name: long names wrap onto further lines (up to a
  per-shape maximum line width) and the state grows, around its centre, until
  the text fits inside the outline. It updates live while typing, applies on
  load, and never goes below the shape's default size. Size is local editor
  layout and is not part of the API.
- A state's name may contain line breaks. In the inline editor Shift+Enter
  inserts one, Enter commits and Escape restores the old name; the Properties
  panel label field is multi-line too. Each explicit line is wrapped on its
  own and the state is sized for all lines, live while typing. Trailing blank
  lines are dropped on commit. Outside the canvas (validation messages, test
  exports and lists) a name is shown on one line, breaks becoming spaces. The
  API's state `name` already allows this, so the contract is unchanged.

## Validation (editor)
- The error/warning count in the canvas toolbar is a button: it opens the
  Validation tab of the bottom panel, un-collapsing the panel if it was hidden.
  A valid model shows a plain indicator that does nothing.
- Clicking an issue row (or pressing Enter/Space on it) selects the state or
  transition it concerns and pans it into view when it is off-screen; zoom is
  left alone. A row without an element is not clickable.
- Double-clicking a state's test chips selects the state, opens the right panel
  on the Test Cases tab and scrolls the list into view, highlighting it
  briefly. The gaps between chips are part of the control.
- Test Cases is a tab of its own and the right panel's default, because test
  cases are what the tool is for. With a state selected it edits that state's
  cases; with nothing selected it lists the states that have any, so the tab is
  never empty for no reason. The tab shows the model's total.
- The test case overlay closes only through Save, Cancel or the close button in
  its top-right corner. Clicking the backdrop, releasing a text-selection drag
  outside the dialog, and pressing Escape do not close it, so unsaved edits are
  never lost by accident.

## Test Cases page (FR-004, FR-005, FR-024)
- Lists every test case across all projects, one row per case, with its
  Component > Scenario > Model › State path. Double-clicking a row edits its
  Gherkin.
- **Filters**: project, component, scenario and model dropdowns cascade:
  each only offers values inside the levels above it, and changing a level
  clears the levels below. Category chips are multi-select (none = all); type
  (positive/negative) is single-select; a links filter narrows to cases with or
  without an implementation link, with a backlog item, or with no links. Search
  matches the id, name, path, state and the Given/When/Then text. A "Clear
  filters" button appears with the number of active filters.
- **Sorting**: every data column header sorts; clicking the active header flips
  the direction, and `aria-sort` reflects it. The id sorts by model, then
  numerically by sequence, so `M_2` precedes `M_10`. Ties fall back to the id.
- **Grouping**: by project, component, scenario, model, state, category or
  type. Each group has a collapsible header row with its path, count and
  positive/negative split; the column sort applies within groups. Expand all /
  Collapse all are offered while grouped.
- The summary tiles and the Gherkin export cover exactly the filtered rows.
- Filters, sort and grouping are remembered in browser storage; they are a
  per-browser convenience, not stored server-side.

## Traceability page (FR-025 to FR-028)
- **Requirement means backlog item.** A requirement is identified by the backlog
  link of a test case (its `backlogUrl`); there is no separate requirement
  entity. Links that differ only by trailing slash, fragment or the case of the
  scheme and host are one item. The implementation link (`implementationUrl`) is
  the code or work that realises a test case. Both are fields of the test case,
  set in the test case editor, and must be full http(s) URLs.
- The page is `GET /projects/{projectId}/traceability` for one project, chosen
  in a dropdown (it opens on the first). Component and scenario dropdowns
  cascade as on the Test Cases page.
- **Matrix tab**: one row per test case, grouped under its backlog item (rows
  with no backlog link are grouped as "No backlog item"). Columns: backlog item,
  test case, Component › Scenario, number of assigned model elements, and
  implementation link. A gap dropdown (any trace, no backlog item, no
  implementation, no model element) is applied by the server; the search box
  matches test case name, backlog URL and implementation URL in the shown rows.
- **Gaps tab**: three tiles with the counts of the gap types, each selecting
  that gap and listing it: test cases without a backlog item, test cases of a
  backlog item without an implementation link, and backlog items whose test
  cases are assigned to no state or transition. The counts do not change with
  the gap or search.
- A test case name opens the test case editor (through the Test Cases page,
  `?open=<testCaseId>`). Links open in a new tab with `rel="noopener noreferrer"`;
  a value that is not http(s) is shown as text, never as a link.
- **Export CSV** writes the shown rows, one line per backlog item and test case
  pair (an untraced test case has an empty backlog cell). Cells that start with
  `=`, `+`, `-` or `@` are prefixed with `'`, so a spreadsheet does not run them.
- Test results are not part of this page.

## AI chat panel (FR-030 to FR-034)
- The chat is the right column's third tab, after Test Cases and Properties,
  and keeps its transcript while the user switches tabs. Opening another model
  clears it: its proposals belong to the feature that was open.
- Before the first request of a turn the panel syncs the open model's project,
  component, feature and graph to the backend and reuses the resulting ids
  afterwards, because the AI endpoints are scoped to a feature the backend
  knows (ADR 0006).
- A message is turned into a `POST /ai/proposals` request. The requested kind is
  either chosen explicitly in the composer or inferred from the message:
  test cases -> `test-cases`, scenario description -> `feature-description`,
  states/transitions -> `states-and-transitions`, whole model -> `model`.
- The panel polls `GET /jobs/{id}` until the job finishes, then loads each
  proposal and renders it as a card with its rationale, its source model and
  Accept / Reject.
- Accept calls `POST /proposals/{id}/accept` and only then applies the payload
  to the open model: a test case is attached to the selected state, a scenario
  description replaces the model's scenario text, states and transitions are
  added to the canvas. Nothing is applied before the user accepts (FR-033).
- Errors are shown in the transcript using the problem detail returned by the
  API. The one prerequisite the panel cannot satisfy itself is an AI provider
  configured in Settings; a model that is not in the tree at all is reported as
  such, because there is no feature to ask about.

## Behaviors
- Proposals appear as ghost elements on the canvas until accepted.
- Unsaved changes are indicated; conflicts (version mismatch) prompt reload/merge.
- Keyboard-accessible alternative to canvas editing (table view of states/transitions).
