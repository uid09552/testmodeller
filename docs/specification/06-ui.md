# UI

## Screens
1. **Projects**: the Project > Component > Feature > Model tree is the left
   navigation bar's main content, under the heading "Projects". There is no nav
   item for it — it is always there — and the cross-cutting views stay listed
   below it. Selecting a project, component or feature opens the Explorer page,
   which shows its detail.
2. **Model editor**: canvas (states, transitions), right panel with three tabs
   — Test Cases, Properties and AI — validation/test-case/scenario tabs in the
   bottom panel, undo/redo, version history.
3. **Test cases**: generate dialog (criterion, seed), result list, coverage summary, diff on regenerate, export.
4. **Coverage dashboard**: per component/feature coverage and uncovered elements.
5. **AI assistant**: chat panel in the editor's right column, and a proposal
   list page; prompt input, proposal cards with accept/reject and rationale.
6. **Settings**: shows the AI provider in effect, read-only, and how to change
   it in `.env`; the provider is configured in the environment, not here.

There is no model overview screen. A model is opened straight from the tree.

## Layout
```
+-----------+--------------------------------+-------------+
| Nav bar   |  Model canvas                  | Test cases  |
| + tree    |                                | | Props     |
|           |                                | | AI chat   |
+-----------+--------------------------------+-------------+
| Validation | Test cases | Coverage (bottom tabs)         |
+--------------------------------------------------------- +
```

## Navigation
- The tree is rendered once, in the nav bar, and is shared by every screen. It
  has no nav item of its own: collapsing the nav to icons is what hides it,
  because at that width there is no room for a tree.
- Single-clicking a model in the tree opens it in the model editor. Clicking a
  project, component or feature selects it and shows its detail on the Explorer
  page.
- Navigating to a model passes the feature id along, because the AI endpoints
  are scoped to a feature.

## Canvas tools
- The toolbar carries a select/pan pair next to Align, as a segmented control:
  they are modes, so the active one stays lit. `V` selects, `H` pans.
- **Select** is the editing default: dragging the background marquee-selects,
  dragging a state moves it, and the connector dots are offered on hover.
- **Pan** is the hand tool: a left-drag moves the view wherever it starts, over
  a state as readily as over the background, and no connector dots are offered.
  The cursor is `grab`, and `grabbing` while dragging.
- Middle-mouse and Shift/Alt + left-drag pan in either mode, so panning never
  requires switching tool.
- Double-clicking empty canvas centres the diagram. It does not add a state: an
  easy gesture should not be destructive on a diagram being read. States are
  added from the palette, by dragging off a connector dot, or from the
  right-click menu.

## Test case visibility (FR-033)
- Each state on the canvas carries a chip per test category (`U`/`I`/`F`) with
  its count, and a dot when the category contains a negative case. The chips
  are the primary signal that a state is covered, so they are rendered at
  readable size with filled, high-contrast backgrounds.
- The chips sit just below the state, not inside it: at a readable size they
  covered the state's own name.
- A state sizes itself to its name: long names wrap onto further lines (up to a
  per-shape maximum line width) and the state grows, around its centre, until
  the text fits inside the outline. It updates live while typing, applies on
  load, and never goes below the shape's default size. Size is local editor
  layout and is not part of the API.
- Double-clicking a state's test chips selects the state, opens the right panel
  on the Test Cases tab and scrolls the list into view, highlighting it
  briefly. The gaps between chips are part of the control.
- Test Cases is a tab of its own and the right panel's default, because test
  cases are what the tool is for. With a state selected it edits that state's
  cases; with nothing selected it lists the states that have any, so the tab is
  never empty for no reason. The tab shows the model's total.
- The test case overlay closes only through Save, Cancel or the close button in
  its top-right corner. Clicking the backdrop, releasing a text-selection drag
  outside the dialog, and pressing Escape do not close it, so unsaved edits are
  never lost by accident.

## Test Cases page (FR-004, FR-005, FR-024)
- Lists every test case across all projects, one row per case, with its
  Component > Scenario > Model › State path. Double-clicking a row edits its
  Gherkin.
- **Filters**: project, component, scenario and model dropdowns cascade:
  each only offers values inside the levels above it, and changing a level
  clears the levels below. Category chips are multi-select (none = all); type
  (positive/negative) is single-select; a links filter narrows to cases with or
  without an implementation link, with a backlog item, or with no links. Search
  matches the id, name, path, state and the Given/When/Then text. A "Clear
  filters" button appears with the number of active filters.
- **Sorting**: every data column header sorts; clicking the active header flips
  the direction, and `aria-sort` reflects it. The id sorts by model, then
  numerically by sequence, so `M_2` precedes `M_10`. Ties fall back to the id.
- **Grouping**: by project, component, scenario, model, state, category or
  type. Each group has a collapsible header row with its path, count and
  positive/negative split; the column sort applies within groups. Expand all /
  Collapse all are offered while grouped.
- The summary tiles and the Gherkin export cover exactly the filtered rows.
- Filters, sort and grouping are remembered in browser storage; they are a
  per-browser convenience, not stored server-side.

## AI chat panel (FR-030 to FR-034)
- The chat is the right column's third tab, after Test Cases and Properties,
  and keeps its transcript while the user switches tabs. Opening another model
  clears it: its proposals belong to the feature that was open.
- Before the first request of a turn the panel syncs the open model's project,
  component, feature and graph to the backend and reuses the resulting ids
  afterwards, because the AI endpoints are scoped to a feature the backend
  knows (ADR 0006).
- A message is turned into a `POST /ai/proposals` request. The requested kind is
  either chosen explicitly in the composer or inferred from the message:
  test cases -> `test-cases`, scenario description -> `feature-description`,
  states/transitions -> `states-and-transitions`, whole model -> `model`.
- The panel polls `GET /jobs/{id}` until the job finishes, then loads each
  proposal and renders it as a card with its rationale, its source model and
  Accept / Reject.
- Accept calls `POST /proposals/{id}/accept` and only then applies the payload
  to the open model: a test case is attached to the selected state, a scenario
  description replaces the model's scenario text, states and transitions are
  added to the canvas. Nothing is applied before the user accepts (FR-033).
- Errors are shown in the transcript using the problem detail returned by the
  API. The one prerequisite the panel cannot satisfy itself is an AI provider
  configured in Settings; a model that is not in the tree at all is reported as
  such, because there is no feature to ask about.

## Behaviors
- Proposals appear as ghost elements on the canvas until accepted.
- Unsaved changes are indicated; conflicts (version mismatch) prompt reload/merge.
- Keyboard-accessible alternative to canvas editing (table view of states/transitions).
